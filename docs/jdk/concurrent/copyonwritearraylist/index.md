# CopyOnWriteArrayList：读快照与写时复制

`CopyOnWriteArrayList` 适合“读远多于写、集合规模可控、允许读到稍旧快照”的场景。它并不是让读写共同操作一个可变数组，而是让每次写操作创建并发布一个新数组；已经拿到旧数组的读线程继续安全地读取旧快照。

本专题以 OpenJDK 8u 的 `java.util.concurrent.CopyOnWriteArrayList` 为主基线，并单独说明 JDK 17/21 的锁实现变化。稳定契约来自公开 API，`lock` 类型和批量操作的内部算法属于版本相关实现。

## 先建立三条不变量

1. `array` 指向一份发布后不再原位修改的 `Object[]`。
2. 普通读取只获取一次数组引用，然后在这一份快照上完成整个操作。
3. 写线程串行执行“读取当前数组、复制、修改副本、发布新数组”。

只要第三条成立，读线程就不需要在访问元素时加锁。旧数组仍被迭代器或读线程引用时也不会失效，等引用全部消失后再由垃圾收集器回收。

## JDK 8 的关键字段

| 字段或方法 | JDK 8 角色 | 阅读重点 |
| --- | --- | --- |
| `final transient ReentrantLock lock` | 串行化所有修改操作 | 保护的是写入流程，不是每次读取 |
| `transient volatile Object[] array` | 当前已发布快照 | `volatile` 建立新数组发布的可见性 |
| `getArray()` | 读取一次当前数组引用 | 后续查找应在同一引用上完成 |
| `setArray(Object[])` | 发布新快照 | 不会逐项修改旧数组 |

`size()`、`get()`、`contains()` 等读取路径都不获取写锁。它们先执行 `getArray()`，再使用得到的局部变量。这不仅减少同步开销，也避免一次操作中混用两个不同版本的数组。

## get 的最短调用链

```text
get(index)
  -> getArray()
  -> get(elements, index)
  -> (E) elements[index]
```

一次 `volatile` 读取拿到数组引用后，元素读取就是普通数组访问。这里的“一致”指当前方法使用同一份数组快照，不代表多个独立的 `get()` 调用一定观察到同一个版本。

## add 的写入主线

```text
add(element)
  -> lock.lock()
  -> elements = getArray()
  -> newElements = Arrays.copyOf(elements, len + 1)
  -> newElements[len] = element
  -> setArray(newElements)
  -> lock.unlock()
```

写锁不能省略。两个写线程如果同时基于同一份旧数组复制，各自发布新数组，后发布者会覆盖先发布者的结果。锁使第二个写线程在拿到锁后重新读取最新数组，从而把两次修改串联起来。

## volatile 在这里保证什么

写线程先填充新数组，随后把数组引用写入 `volatile array`。之后读线程通过 `getArray()` 读到该新引用时，能够看到发布前对新数组完成的元素写入。

需要区分两个概念：

- `volatile` 负责新数组的安全发布和可见性。
- 写锁负责多个复合写操作之间不丢失更新。

只有 `volatile` 无法把“复制并追加”变成原子复合操作；只有写锁而没有可靠发布，也不能让无锁读线程及时看到新数组。

## 成本模型

| 操作 | 时间复杂度 | 额外空间 | 是否获取写锁 |
| --- | --- | --- | --- |
| `get(index)` | O(1) | O(1) | 否 |
| `contains` | O(n) | O(1) | 否 |
| `add` | O(n) | O(n) | 是 |
| 中间 `set/remove` | O(n) | O(n) | 是 |
| 创建迭代器 | O(1) | O(1)，共享当前数组 | 否 |

“读无锁”不是免费午餐。写入会复制整个引用数组，短时间内新旧数组还可能同时存活，因此大集合、高频写入或对内存抖动敏感的场景不适合它。

## 适用与不适用

适合：

- 监听器、订阅者和规则快照，注册变化很少但遍历频繁。
- 配置项数量较少，读线程可以接受事件发生前创建的迭代器继续读取旧版本。
- 遍历期间不希望持锁，也不要求迭代器快速失败。

不适合：

- 高频追加、删除或更新的大列表。
- 需要读取后立刻基于最新值执行条件写入，但没有使用容器提供的原子复合方法。
- 依赖迭代器观察遍历期间新增元素的业务。

## JDK 8 到 JDK 17/21

JDK 8 使用 `ReentrantLock` 保护写入。JDK 17/21 的实现改为 `Object` 锁对象配合内置监视器，并重写了部分批量删除算法。变化不影响公开语义：读取基于不可变快照，修改仍复制并发布新数组，迭代器仍不支持修改。

调试时必须以当前 SDK 源码为准，不要把 `lock.lock()` 这一具体断点当成跨版本稳定入口。更稳定的定位方式是公开写方法、`getArray/setArray` 和新数组发布点。
