# LongAdder：写入分散、汇总与版本边界

`LongAdder` 面向高竞争统计计数。它不维护一个随时可线性化读取的“唯一当前值”，而是让更新落到 `base` 或某个 `Cell.value`，在读取时把这些位置相加。

## sum 如何读取逻辑总量

`sum()` 的调用链非常直接：

```text
sum = base
for 每个非空 Cell:
  sum += Cell.value
return sum
```

在所有写线程停止并建立了正确的线程间可见性之后，返回值应等于全部已完成累加。并发写入期间，它没有冻结更新线程，也没有一次性读取所有位置：

| 时刻 | 汇总线程 | 更新线程 |
| --- | --- | --- |
| t1 | 读取 `base` | 尚未累加 |
| t2 | 读取 `Cell[0]` | 随后更新已读过的 `Cell[0]` |
| t3 | 尚未读取 `Cell[1]` | 更新 `Cell[1]` |
| t4 | 读取 `Cell[1]` | 已完成 |

这次 `sum()` 可能包含 t3 的更新，却不包含更早发生在 t2 的更新。结果不是某个单一时刻的快照，不能用来证明“此前没有更新”或驱动严格余额判断。

## sumThenReset 为什么需要静默期

`sumThenReset()` 逐个取得 `base` 和 Cell 的值，并把每个位置归零。跨条带没有一把总锁，因此它和并发 `add` 之间不存在一个全局切割点。

OpenJDK 8u 的实现对每个位置执行“读取，再直接写零”。如果更新线程恰好在读取后、写零前 CAS 成功，这次更新可能被零覆盖。JDK 17/21 改为对 `base` 和每个 Cell 分别执行原子 get-and-set，减少单个位置上的读零竞态，但仍然是逐个条带处理：

- 较早访问的条带已经归零时，后续更新会留到下一窗口；
- 尚未访问的条带发生更新时，可能计入当前返回值；
- 并发初始化或扩容还可能改变本次捕获的 `cells` 数组边界。

所以三个版本的公开契约都没有变：有并发更新时，返回值不保证是 reset 前的最终值。可靠用法是在明确的静默点执行，例如所有工作线程已结束并 `join` 后，或通过外部协议暂停写入后切换统计窗口。

`reset()` 的限制更强：它只清零而不返回旧总量，同样只适用于确定没有并发更新的场景。较新 JDK 的 `reset()` 仍不是跨条带原子操作。

## 为什么 increment 没有返回值

`LongAdder.increment()` 等价于 `add(1)`，返回类型为 `void`。一次更新可能落在任意条带，若要返回严格的新总量就必须同步汇总其他条带，这会破坏分散写入的主要优势。

因此它适合：

- 请求次数、命中次数、已处理事件数；
- `ConcurrentHashMap<K, LongAdder>` 形式的热点频次统计；
- 允许读取近似瞬时值、最终需要静默期精确汇总的指标。

它不适合：

- 生成唯一连续序号；
- 根据“递增后的准确总值”立即触发唯一动作；
- 库存、余额、并发额度等需要校验后扣减的状态；
- 需要把读取与清零在线性化点严格分开的滚动窗口。

## 与 ConcurrentHashMap 组合

常见频次表可以写成：

```java
frequencyMap.computeIfAbsent(key, ignored -> new LongAdder()).increment();
```

这里有两个不同的原子边界：

1. `computeIfAbsent` 按 `ConcurrentHashMap` 的规则为单个键安装值。
2. `LongAdder.increment` 在该计数器内部选择 `base` 或 Cell 累加。

它们不构成跨键事务。遍历 Map 并调用各个 `sum()` 得到的报表，也不是所有键在同一时刻的快照。

## 空间和缓存边界

每个 `Cell` 都带有 `@Contended`，JVM 可借助填充降低相邻 Cell 共享缓存行导致的伪共享。物理对象尺寸和缓存行布局属于 VM 与硬件实现细节，不能按某个固定字节数做业务容量计算。

相较单个 `AtomicLong`，LongAdder 可能持有：

- 一个二次幂长度的 Cell 引用数组；
- 多个带竞争填充的 Cell 对象；
- 已经不再被活跃线程命中的历史槽位。

所以“高竞争写入更快”换来的是更高空间占用、O(n) 汇总和更弱的并发读取语义。

## sumThenReset 的调用边界

如果要按时间窗口采集指标，优先考虑下面两种协议：

1. 在任务批次结束、所有生产线程完成后调用 `sumThenReset()`。
2. 通过一个原子引用把业务写入切换到新的 LongAdder，再等待旧写入者退出，最后只汇总旧实例。

第二种方式仍需严谨设计“写入者何时取得引用、何时算退出”，仅仅 `getAndSet(new LongAdder())` 并不能证明没有线程握着旧引用继续写。若监控允许窗口边界近似，则可以接受较弱协议，但要在指标定义中说清楚。

## 推荐断点

| 方法 | 观察变量 | 验证目标 |
| --- | --- | --- |
| `LongAdder.add` | `cells/as`、`base/b`、目标 `Cell`、`uncontended` | 快路径如何升级到慢路径 |
| `LongAdder.sum` | `base`、数组引用、各 Cell 的 `value` | 汇总不是原子快照 |
| `LongAdder.sumThenReset` | `sum`、`base`、各 Cell 值 | 逐条带读取和归零 |
| `Striped64.longAccumulate` | probe、`collide`、`cellsBusy` | 初始化、换槽和扩容 |

慢路径的完整状态机见 [Striped64：longAccumulate](./striped64.md)。
