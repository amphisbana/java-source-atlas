# resize 扩容机制

`resize()` 同时承担两种职责：第一次创建桶数组，以及已有数组容量翻倍后的节点迁移。

### 三个节点为什么只有两个目的地

| 节点 | hash（二进制低 4 位） | `hash & oldCap` | 新下标 |
| --- | --- | ---: | ---: |
| A | `0001` | 0 | 1 |
| B | `0101` | 4 | 5，即 `1 + oldCap` |
| C | `1001` | 0 | 1 |

旧掩码已经确定低两位为 `01`。新容量为 8 时，掩码只新增 `0100` 这一位，所以结果不可能跳到其他桶。这也是 `resize` 不必再次调用键的 `hashCode()` 的原因。

### 迁移循环中必须同时盯住的引用

| 变量 | 作用 | 迁移完成时的不变量 |
| --- | --- | --- |
| `loHead / loTail` | 收集 oldCap 位为 0 的节点 | 分组内顺序与旧链一致 |
| `hiHead / hiTail` | 收集 oldCap 位为 1 的节点 | 分组内顺序与旧链一致 |
| `next` | 暂存当前节点的旧后继 | 改写 `e.next` 前不能丢失 |
| `newTab[j]` | 接收低位链 | 尾节点的 `next` 必须为 null |
| `newTab[j + oldCap]` | 接收高位链 | 尾节点的 `next` 必须为 null |

调试时在链表迁移循环尾部停住，依次观察 `e`、`next`、`loTail`、`hiTail`。如果只看最终 `newTab`，会错过源码如何在原节点上改写 `next`，也无法理解为什么不创建新的键值节点。

::: info 扩容复制数组，不复制键和值
`new Node[]` 创建的是新桶数组；普通链表迁移复用已有 `Node` 对象。扩容成本来自扫描旧桶和重连节点，而不是克隆业务对象。
:::

## 新容量和新阈值

它先读取：

```text
oldTab   旧桶数组
oldCap   旧容量
oldThr   旧 threshold
```

再按状态决定新值：

| 状态 | 新容量 | 新阈值 |
| --- | --- | --- |
| 已有数组且未到最大容量 | 通常是 `oldCap × 2` | 通常是 `oldThr × 2` |
| 构造器保存了计划容量 | 使用 `oldThr` 作为容量 | 按容量和负载因子计算 |
| 无参构造且第一次写入 | 16 | 12 |
| 已到最大容量 | 不再扩容 | 阈值设为整数最大值 |

“通常”是因为最大容量、较小初始容量和自定义负载因子会使代码进入不同边界分支。

## 为什么扩容不需要重新做完整定位

假设旧容量为 16，新容量为 32：

```text
oldCap      = 0001 0000
oldMask     = 0000 1111
newMask     = 0001 1111
```

新掩码只比旧掩码多检查一个二进制位，也就是 `oldCap` 对应的位。因此一个节点扩容后只有两个去向：

```text
(hash & oldCap) == 0  →  仍在原下标 j
(hash & oldCap) != 0  →  移动到 j + oldCap
```

不需要重新调用键的 `hashCode`，节点内缓存的扰动哈希已经足够。

## 三类桶的迁移

### 单节点

桶中只有一个节点时，直接使用 `e.hash & (newCap - 1)` 计算新位置。

### 链表

JDK 8 把原链表拆成两条：

```text
低位链 lo：hash & oldCap == 0  → newTab[j]
高位链 hi：hash & oldCap != 0  → newTab[j + oldCap]
```

迁移使用头尾指针追加节点，保持每个分组中节点的原相对顺序。完成后把两条链的尾节点 `next` 置空，避免仍然连接到旧链。

示例：旧容量为 16，两个哈希的旧低 4 位相同，因此都在桶 3：

```text
hash A = ...0 0011  → 扩容后仍在 3
hash B = ...1 0011  → 扩容后移动到 3 + 16 = 19
```

### 红黑树

树桶调用 `TreeNode.split`，同样按 `oldCap` 对应位分成低、高两组。拆分后：

- 分组节点数较少时退化为链表；
- 节点仍足够多时重新组织为树；
- 如果只有一侧有节点，可以保留已有树结构。

## 扩容成本

单次扩容需要遍历旧数组和全部已有节点，时间复杂度为 O(capacity + size)。均摊到多次正常写入后，`put` 的预期成本仍接近常数时间。

可以提前设置合理初始容量来减少扩容，但过大的容量也有代价：迭代 HashMap 的成本与“容量 + size”相关，因为迭代器需要扫描桶数组。

## 并发边界

JDK 8 的尾部拆分修复了 JDK 7 头插迁移可能形成环形链表的特定问题，但这不意味着 `HashMap` 变成线程安全。并发写入仍可能出现：

- 更新丢失；
- 可见性问题；
- 结构状态竞争；
- 迭代结果不确定或抛出 `ConcurrentModificationException`。

需要并发读写时，应根据场景使用 `ConcurrentHashMap` 或通过外部同步保护整个复合操作。
