# 链表树化

## 为什么引入红黑树

哈希分布正常时，每个桶通常只有很少节点。但恶意或质量差的 `hashCode` 可能让大量键集中到同一个桶，链表查找会退化到 O(n)。JDK 8 在满足条件时把长链表转换为红黑树，使树内查找的复杂度变为 O(log n)。

树节点比普通节点占用更多内存，所以短桶仍然使用链表。

## treeifyBin 并不总是树化

调用 `treeifyBin(table, hash)` 后先检查数组容量：

```text
table 容量 < MIN_TREEIFY_CAPACITY(64)
  └─ resize()，优先增加桶数量来分散碰撞

table 容量 >= 64
  └─ 把该桶的 Node 链转换为 TreeNode 链，再组织红黑树
```

原因是小数组中的碰撞很可能只是容量不足，扩容比维护树结构更划算。只有容量已经较大而碰撞仍然集中时，树化才更有价值。

## 为什么实验插入 9 个碰撞键

`putVal` 的链表计数从遍历桶首节点之后开始，追加节点后再判断是否达到 `TREEIFY_THRESHOLD - 1`。为避免把循环计数和最终链长混淆，本项目用以下稳定场景触发树化：

```java
Map<CollisionKey, String> map = new HashMap<>(64);
for (int i = 0; i < 9; i++) {
    map.put(new CollisionKey(i, 7), "value-" + i);
}
```

所有键返回相同哈希，初始容量已经满足 64，第 9 次写入会经过树化判断。具体树形不属于公开契约，不应该在业务代码或测试中依赖。

## TreeNode 如何比较键

树节点查找不能只依赖哈希值，因为多个不同键可以拥有相同哈希。核心决策顺序是：

1. 哈希值较小，进入左子树；较大，进入右子树。
2. 哈希相同且键相等，命中节点。
3. 哈希相同但键不等，若键类型一致且实现 `Comparable`，尝试自然顺序。
4. 仍无法确定时，使用类名和对象身份相关的顺序打破平局，并在必要时搜索两侧子树。

平局规则的目标是提供稳定的树结构方向，不会替代 `equals` 的键相等语义。

## 链表关系为什么仍然保留

`TreeNode` 除了 `parent`、`left`、`right` 和颜色，还保留 `next` 与 `prev`。桶内链表关系用于：

- 与数组桶首节点衔接；
- 迭代所有节点；
- 删除和反树化；
- 扩容时拆分树桶。

`moveRootToFront` 会把树根移动到桶链表头，缩短后续树查找的入口路径。

## 红黑树必须保持的性质

- 每个节点是红色或黑色。
- 根节点是黑色。
- 红色节点的子节点不能是红色。
- 从任意节点到其后代空节点的路径具有相同数量的黑色节点。

插入后通过旋转和变色恢复约束；删除后也有相应平衡过程。理解 `HashMap` 时应先掌握“什么时候进入树逻辑”，不必把所有红黑树旋转细节混在 `putVal` 主流程中。

## 反树化不是一句“少于 6”

`UNTREEIFY_THRESHOLD = 6` 主要用于扩容时树桶拆分后的分组判断。删除树节点时，源码还会根据根、左右孩子等结构条件判断是否退化为链表。因此：

> 不能把“节点数小于等于 6 时必然立即反树化”当成所有场景都成立的公开规则。

树化、反树化都是内部性能策略。业务代码只能依赖 Map 行为，不能依赖当前桶究竟是链表还是树。
