# 版本差异与边界

先在 [JDK 8 / 17 / 21 版本对比工作台](/jdk/version-comparison/) 选择 HashMap，可并排核对三个固定 Tag 的真实源码坐标、方法状态和迁移影响；本页继续补充 JDK 7 到 JDK 8 的结构性变化与使用边界。

## JDK 7 与 JDK 8

| 主题 | JDK 7 | JDK 8 及以后主线 |
| --- | --- | --- |
| 桶结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
| 节点类型 | `Entry` | `Node` / `TreeNode` |
| 哈希扰动 | 多次移位异或 | 高 16 位与低 16 位异或 |
| 链表迁移 | 重新定位并采用头插思路 | 按 `oldCap` 位拆成高低链，保持组内相对顺序 |
| 极端碰撞 | 查找退化为 O(n) | 满足条件后树查找为 O(log n) |

JDK 8 改善了扩容迁移和极端碰撞性能，但没有改变 `HashMap` 非线程安全的契约。

## JDK 8、17 与 21

核心设计保持稳定：

- 延迟分配桶数组；
- 容量保持 2 的幂；
- 使用高低位异或进行哈希扰动；
- 桶使用链表或红黑树；
- 扩容按 `oldCap` 对应位拆分节点；
- 使用 `modCount` 支持迭代器快速失败检查。

阅读时仍要注意方法签名、内部辅助类和安全检查接口可能变化。例如不同版本的 `getNode` 参数形式、序列化数组检查入口和局部实现可能不同。不要把某个版本的源码行号或私有方法签名写入业务依赖。

JDK 19 起提供 `HashMap.newHashMap(int numMappings)`，调用者可以直接表达预计映射数量，由 JDK 换算出合适容量。JDK 8 和 JDK 17 没有这个静态工厂。

## 复杂度边界

| 操作 | 哈希分布正常 | 极端碰撞且已树化 | 最坏边界说明 |
| --- | --- | --- | --- |
| `get` | 预期 O(1) | O(log n) | 不满足树化条件时仍可能 O(n) |
| `put` | 预期 O(1)，均摊 | O(log n) | 扩容单次 O(capacity + size) |
| `remove` | 预期 O(1) | O(log n) | 还涉及链表或树结构调整 |
| 完整迭代 | O(capacity + size) | O(capacity + size) | 大量空桶也需要扫描 |

## 使用边界

### 不适合并发写

多线程共享且存在写操作时，使用 `ConcurrentHashMap` 或外部同步。`Collections.synchronizedMap` 能包装基本操作，但遍历和复合操作仍需要按其文档手动同步。

### 不提供顺序

当前环境中碰巧稳定的遍历结果不是契约。需要顺序时明确选择 `LinkedHashMap` 或 `TreeMap`。

### 可变键会破坏可查找性

键进入 HashMap 后，修改参与 `hashCode` 或 `equals` 的字段，可能让节点停留在旧桶而查询转向新桶。优先使用不可变对象作为键。

### 自定义 hashCode 仍然重要

哈希扰动只能混合高低位，无法修复所有对象都返回同一个哈希的问题。高质量 `hashCode` 应让业务数据尽量均匀分布，并与 `equals` 保持一致。

## 本专题没有承诺什么

- 不承诺私有字段和私有方法跨 JDK 版本稳定。
- 不通过反射读取 `table` 作为业务用法。
- 不把红黑树具体形态、桶下标或遍历顺序写成 API 契约。
- 不把本专题当作 `ConcurrentHashMap` 的并发实现说明。
