# 如何阅读一个源码主题

源码阅读不是从类的第一行读到最后一行。建议始终从可观察行为出发，再进入对应分支。

## 四步阅读法

1. **运行案例**：先看到输入、输出和行为边界。
2. **固定入口**：从公开 API 进入，不在内部方法之间无目标跳转。
3. **只跟目标分支**：一次只解释一个场景，例如首次写入或扩容。
4. **返回测试**：用断言确认源码推导与公开行为一致。

## 在站点中完成一次学习闭环

每个专题建议按下面的顺序完成，不要把“读过正文”直接当成“已经掌握”：

| 阶段 | 使用入口 | 要留下的结果 | 完成判断 |
| --- | --- | --- | --- |
| 定位 | [完整学习路线](/learning-path/) | 当前阶段、先修专题和本次目标 | 能说清为什么现在读这个类 |
| 建模 | 专题主线与动画 | 一张公开入口到核心方法的调用链 | 能在播放前预测下一次状态变化 |
| 核对 | [源码索引](/source-explorer/) | 固定版本源码入口和推荐断点 | 能在 IDE 中准确命中目标分支 |
| 比较 | [JDK 版本对比](/jdk/version-comparison/) | 版本变化及对应用法的影响 | 能区分 API 变化和内部实现变化 |
| 验证 | 专题断点实验 | 控制台结果、断点变量和测试断言 | 能用最小输入复现关键分支 |

路线页和源码索引共用浏览器本地学习进度。只有正文和实验都完成，才算完成一个专题；清除站点数据或更换浏览器后，本地进度不会自动同步。

### 怎样使用可执行证据链

每个专题首页都会给出至少一条“可执行证据链”，它不是延伸阅读清单，而是一条可以逐段核对的结论：

1. 先读结论，明确这次要验证的公开行为，而不是笼统地“看看源码”。
2. 从证据指定的源码入口进入对应讲解，确认关键分支和版本边界。
3. 运行同一条证据列出的 Lab 方法，在断点中观察结论依赖的状态。
4. 打开精确到类和方法的 JUnit 测试，确认公开行为已经由断言固定。

这些关联由 `source-index` 统一维护。文档构建会检查入口与讲解是否成对存在、Lab 方法是否真实存在、测试类路径是否正确，以及测试方法是否带 `@Test`。因此某个类或方法重命名后，CI 会直接指出断开的证据，而不会让页面保留一条看似完整但无法运行的说明。

### 第一次只追一条路径

框架和并发类经常有大量支路。第一次进入源码时，先写下“输入、目标分支、期望状态”三个约束，例如：

```text
输入：HashMap 第 13 个元素，当前容量 16，负载因子 0.75
目标分支：putVal 触发 resize
期望状态：容量变为 32，旧桶节点按 oldCap 位拆成低位链和高位链
```

只在这一条路径上单步，遇到异常、删除、序列化等无关支路先返回。完成一次确定路径后，再换输入研究下一条分支。

## 如何使用源码动画

动画不是正文的替代品，而是把一次确定的源码分支拆成可观察快照。建议按以下顺序使用：

1. 先停在第一步，读清场景的初始容量、线程数、队列长度或同步状态。
2. 点击“下一步”，只比较当前快照与上一步发生变化的字段和节点。
3. 对照动画下方的方法名，在 IDE 中进入同名源码并设置断点。
4. 完成单步理解后再自动播放，检查自己能否提前说出下一次状态变化。
5. 最后运行对应实验，用测试验证公开行为，用断点验证内部字段。

动画中的颜色只表达当前步骤的角色：绿色表示当前目标或成功路径，红色表示碰撞、竞争、转移或拒绝等需要注意的分支。不能把颜色当作 JDK 源码中的真实字段。

### 并发动画的边界

并发主题使用确定步骤重建一种合法执行顺序，目的是解释协调协议，不是模拟操作系统调度，也不是性能基准。实际运行时：

- 线程可能在任意安全点被挂起或恢复；
- CAS 可能因其他线程抢先修改而失败并重试；
- 线程池任务可能在后续任务提交前已经完成；
- `unpark` 只允许线程继续竞争，不保证它立刻获得锁。

因此应把动画理解为“什么状态允许进入哪个源码分支”，不要理解为“线上运行必然按这个时间顺序发生”。

## 如何使用版本信息

文档中的源码位置使用“仓库 + 版本 + 类 + 方法签名”标识。行号只用于当前链接的辅助定位，因为上游提交会让行号发生变化。

## 如何判断自己读懂了

不要背诵常量。能够回答“什么输入触发哪个分支、关键变量怎样变化、最终产生什么公开行为”，才算完成一个主题。
