# Lab 编写规范

Lab 的职责是把一条源码结论变成可以重复运行的观察。它不需要模拟整个生产系统，但必须稳定触发目标分支，并让读者知道应该在哪个方法停下来。

## 最小结构

一个合格的 Lab 至少包含：

1. 一个公开 API 入口和明确的输入条件。
2. 一个能够重复运行的主类或 JUnit 测试。
3. 与专题索引对应的推荐断点和观察变量。
4. 结果断言，验证对外可观察行为，而不是只打印日志。
5. 运行命令、JDK/框架版本和清理方式。

## 编写步骤

### 1. 先写问题和触发条件

用一句话说明实验要回答什么，例如“队列满时，线程池如何在工作队列、最大线程数和拒绝策略之间做选择”。不要从复制源码开始。

### 2. 让状态变化可见

优先使用计数器、线程名、队列长度、状态字段或事件列表记录变化。并发实验要使用 `CountDownLatch`、`CyclicBarrier` 等同步手段固定时序，避免依赖睡眠时间碰运气。

### 3. 把断点写成阅读指引

断点应包含方法签名、触发场景和观察变量。变量名称要能在目标 JDK/框架版本中找到；如果不同版本字段不同，必须在文档中说明。

### 4. 用测试锁住结论

测试只断言公开行为和必要边界，例如返回值、异常类型、顺序、取消结果或资源是否释放。不要把私有字段布局当成跨版本契约。

## 质量检查

提交前运行：

```bash
mvn --batch-mode -pl labs/jdk-labs test
npm run check:source-index
npm run verify:community
```

涉及插件时，再运行 `idea-plugin/./gradlew test buildPlugin --no-daemon`。如果实验需要特定 JDK，请在 README 和 CI 矩阵中明确写出，不要让读者从构建错误中猜版本。

## 常见问题

- 只打印结果，没有断言：读者无法判断实验是否真的覆盖了目标分支。
- 用 `Thread.sleep` 代替同步：本地偶尔通过，CI 或不同机器上会产生假失败。
- 直接依赖 JDK 私有字段：升级后容易失效，应优先观察公开行为并标注内部实现风险。
- 一个 Lab 同时验证多个机制：问题边界不清，建议拆成多个可组合的小场景。
